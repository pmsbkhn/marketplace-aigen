# Chương 2 — Nền tảng: C4 model & ISO/IEC/IEEE 42010

Hai khung tư duy đứng sau mọi file trong `docs/aac/`. Hiểu chúng thì DSL chỉ còn là cú pháp.

## 2.1 C4 model — 4 mức "zoom"

C4 (Context, Containers, Components, Code) của Simon Brown: mô tả kiến trúc ở **4 mức chi
tiết tăng dần**, như Google Maps phóng to.

| Mức | Tên | Trả lời | Khán giả | View trong dự án |
|---|---|---|---|---|
| **L1** | System Context | Hệ thống là gì, ai/cái gì quanh nó? | Mọi người, business | `SystemContext` |
| **L2** | Container | Gồm những app/DB/bus nào triển khai riêng? | Dev, ops, architect | `Containers` |
| **L3** | Component | Bên trong **một** app có khối nào? | Dev của service đó | `*Components` |
| **L4** | Code | Lớp/class cụ thể | (thường để IDE lo) | — không vẽ |

> ⚠️ **"Container" trong C4 ≠ Docker container.** Nó là **một đơn vị chạy/triển khai
> độc lập**: một Spring Boot app, một database, một Kafka. Ví dụ trong dự án:
> `catalogApi` (app), `catalogDb` (PostgreSQL), `kafkaBus` (Kafka) đều là *container*.

Phân cấp lồng nhau:

```
Person ─┐
        ↓ dùng
Software System  (Marketplace System)
   └── Container       (Catalog Service, Catalog Database…)
         └── Component (ProductController, CreateProductUc…)
```

Ví dụ thật trong `docs/aac/model/catalog-context.dsl` — một *container* chứa các
*component*:

```dsl
catalogApi = container "Catalog Service" "..." "Spring Boot 4 / Java 21 / msfw" {
    prodController = component "ProductController" "REST: POST /v1/products..." "Spring MVC" "Ingress"
    createProductUc = component "CreateProductUc" "Tạo sản phẩm (mặc định PENDING)" "Use case"
    catalogDomain = component "Product (Aggregate)" "..." "Domain model (POJO)"
    productOa = component "ProductOa" "Repository<Product>..." "Spring Data JPA"
}
```

L4 (code) cố ý **không** mô hình hoá — class thay đổi liên tục, để IDE/đọc code lo.

## 2.2 ISO/IEC/IEEE 42010 — chuẩn mô tả kiến trúc

Đây là chuẩn quốc tế cho "architecture description". Bốn khái niệm cốt lõi:

| Khái niệm | Nghĩa | Ví dụ trong dự án |
|---|---|---|
| **Stakeholder** | Bên liên quan có lợi ích | PO, dev team, SRE, security |
| **Concern** | Mối quan tâm của stakeholder | "Topology chạy ra sao?", "Dữ liệu nhạy cảm ở đâu?" |
| **Viewpoint** | Khung nhìn đóng khung một tập concern | "góc nhìn triển khai", "góc nhìn bảo mật" |
| **View** | Một sơ đồ/bản mô tả tuân theo viewpoint | `ProdDeployment`, `SecurityBoundaries` |

Một **architecture description** = tập **view** + **correspondence rules** (quy tắc bảo
đảm các view nhất quán với nhau).

## 2.3 Trái tim của AaC: "Một model — nhiều view"

Đây là chỗ C4, 42010 và Structurizr gặp nhau, và là ý quan trọng nhất cả cuốn sách:

> Bạn định nghĩa hệ thống **MỘT LẦN** trong `model { }`. Mỗi **view** chỉ là một **phép
> chiếu/lọc** của model đó cho một stakeholder.

Hệ quả tuyệt vời: **correspondence-by-construction** — các view **không thể mâu thuẫn**,
vì tất cả sinh ra từ cùng một model. Đây chính là điều "cách cũ" (mỗi người vẽ một sơ đồ
rời) không bao giờ làm được.

Minh hoạ bằng chính dự án — cùng một `model/`, năm góc nhìn khác nhau cho năm stakeholder:

```dsl
// docs/aac/views/business.dsl   — PO/business
systemContext marketplaceSystem "SystemContext" "..." { include *; autoLayout tb }

// docs/aac/views/operations.dsl — SRE
deployment marketplaceSystem "Production (k3d)" "ProdDeployment" "..." { include *; autoLayout lr }

// docs/aac/views/security.dsl   — Security
container marketplaceSystem "SecurityBoundaries" "..." { include *; autoLayout lr }
```

Cùng `marketplaceSystem`, chỉ khác **loại view** và **bộ lọc** → ra ba sơ đồ phục vụ ba
mối quan tâm khác nhau, luôn đồng bộ.

## 2.4 Ánh xạ stakeholder → viewpoint → view (bảng tổng)

Đây là "kế hoạch 42010" của dự án, hiện thực trong `docs/aac/views/`:

| Stakeholder | Concern | Viewpoint | View (key) |
|---|---|---|---|
| Business / PO | Hệ thống làm gì, ranh giới ngoài | Context | `SystemContext` |
| Dev team | Cấu trúc nội bộ service | Component | `*Components` (×6) |
| Architect / Integration | Sync vs async, luồng saga | Container + Dynamic | `Containers`, `CheckoutSaga`… |
| Ops / SRE | Topology, hạ tầng, observability | Deployment | `ProdDeployment` |
| Security | Trust boundary, dữ liệu nhạy cảm | Container + tag | `SecurityBoundaries` |
| QA / Governance | Luật kiến trúc không bị phá | (fitness functions) | `*Test.java` trong CI |
